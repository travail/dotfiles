# Global Agent Instructions

## ワークフロー

- 設計上の判断が必要なタスク、または後戻りしにくい・影響範囲が広いタスクは Plan モードで開始する（詳細な経緯は [[feedback_plan_mode_trigger]] 参照）。「新しい種類の仕組みだから」「他プロジェクトへの参照実装になるから」という理由だけでは該当したことにならない。単一ファイル・小規模で後戻りコストが低い変更は、未確定の仕様が AskUserQuestion 等の対話で解消済みならプラン不要（詳細な経緯は [[feedback_plan_mode_calibration_ci_workflow]] 参照）。 Plan モードに入る（プランを書き始める）前に、該当すると判断した具体的な理由を一言説明し、ユーザーの同意を得てから着手する。プランを書き終えてから振り返りで説明するのでは遅い（詳細な経緯は [[feedback_plan_mode_explain_before_writing]] 参照）
- Plan モードを省略できる小規模タスクであっても、隣接する別の承認（仕様の確定、 Issue 作成の許可等）だけで実装着手まで許可されたとは解釈しない。コードの編集・ブランチ／worktree の作成など実装そのものに踏み込む前に、その行為自体への明示的な指示を得る（詳細な経緯は [[feedback_implementation_needs_explicit_go_ahead]] 参照）
- `SendFeedback` は、ユーザーの明示的な指示がない限り呼ばない。全プロジェクト共通、必ず守る
- 実装前に曖昧な点を解消し、詳細な仕様を確認する
- 動作を証明できるまでタスクを完了とマークしない（テスト実行・ログ確認）
- 行き詰まったら無理に進めず、立ち止まって再計画する
- ユーザーからの応答がない場合、勝手な判断で作業を進めない。応答を待つ
- 待機・実行結果確認の処理がタイムアウトした場合、即座に失敗扱いにする／自己判断で代替案を実行するのどちらも避ける。まず対象の実際の状態を直接確認する（タイムアウトは wait 処理自体の一時的な失敗にすぎず、対象の処理自体は完了している場合があることに注意する）。その上で、(a) 進行中の形跡があれば待機をやり直す、(b) 停止・エラー等はっきりしない状態ならユーザーに報告して指示を仰ぐ
- ユーザーの発言が懸念の共有・独り言・ musing なのか、明確な決定表明（「〜にする」「〜でお願いします」等）なのかを区別する。明確な決定表明がない限り、ログ・ Issue ・コード等の永続的な成果物に「決定」として書き込んだり、その前提で作業を進めたりしない。曖昧な場合は確認する。特に承認ゲートが開いている場面（プランのレビュー待ち等）では、「オッケー」「うん」のような具体的な実行指示語を伴わない短い肯定応答だけで実行許可と解釈しない（詳細な経緯は [[feedback_ambiguous_short_ack]] 参照）
- スコープが曖昧な判断（global CLAUDE.md vs project CLAUDE.md、 global settings.json vs project-local settings、全プロジェクトに適用 vs 今回の変更だけに適用、等）は、明示的な指示がない限りデフォルトで狭い方（現在のプロジェクト・現在の変更）を選ぶ。曖昧で誤ると影響が大きい場合は確認する（詳細な経緯は [[feedback_scope_narrow_default]] 参照）

## コーディング原則

- 変更は必要な箇所のみにとどめる。影響範囲を最小化する
- 一時的な修正は避け、根本原因を解決する
- 重要な変更の前に「もっとシンプルな方法はないか？」と一度立ち止まる

## コマンド実行（Auto-Approval ガイドライン）

パーミッションの静的解析および自動承認を阻害せず、不要なユーザー確認（許可申請プロンプト）を発生させないことが全項目の最上位目的である。規律を形式的に守ろうとして別の不要な許可申請（未許可パスへのファイル書き込み等）を誘発しては本末転倒である。状況に応じて、既存の許可済みコマンドや引数を活かし、手動承認を一切発生させない最もシンプルな方法を選択する。

- 複数のコマンドを `&&` や `;`、パイプ等で1行（複合スクリプト）に連結して実行しない。処理を行う際は、原則として1コマンドずつ個別のツール呼び出しに分割して実行する（連結するとパーミッションの自動判定から外れ、不要な実行許可を求められるため）
- `cd` は使用しない。作業ディレクトリの変更が必要な場合は、ツールの作業ディレクトリ指定機能（Cwd パラメータ等）を用いる
- コマンド置換（`$(...)`、バッククォート）を使用しない。サブシェル展開が含まれると動的実行と判定され自動承認が無効化される。パス解決（`$(which ...)` 等）は行わず直接コマンド名で実行し、コマンドが存在せず失敗した場合にのみ探索する
- ファイル生成・編集にシェルを使わない。`cat << 'EOF' > ...` や `echo ... > ...` 等のシェルリダイレクトは複合スクリプトとみなされ承認を要求される。ファイル操作は常に組み込みの `write_to_file` / `replace_file_content` ツールを使用する
- 長文テキスト・マークダウンをコマンドに渡す際は、字句解析の失敗や不要な手動承認の発生を防ぐことを目的とする。複数行の Issue/PR 本文などはシェル上で無理にインライン展開（コマンド置換やヒアドキュメント）を行わず、組み込みの `write_to_file` ツールで一時ファイル（`/tmp/...`）を作成した上で、ファイルオプション（`-F` 等）を用いて単一コマンドで渡す。短く安全な単一行テキストに限りインライン引数（`--body "..."` 等）を直接渡してよい
- 破壊的コマンド（`rm`、`rmdir`、`kill`）のシェル実行を避ける。これらはセキュリティ設計上 allow リストに追加できない。一時ファイルは OS の自動消去（`/tmp`）に委ねて無理に `rm` を実行しないなど、手動承認を誘発するコマンドを最小限にする。バックグラウンドタスクの終了は専用ツール（`manage_task` 等）を用いる
- 複雑な検証や複数処理はシェルワンライナーではなくスクリプトファイル化する。分岐やループをシェルで書くと手動承認が発生し、かといって1手ずつ会話を往復するとトークンを浪費する。`write_to_file` で一時スクリプト（`.py` や `.sh`）を作成し、単一の許可コマンド（`python3` 等）として実行することで、トークン消費を抑えつつ自動承認を両立させる。これもスクリプト作成に手動承認を要しない前提での工夫であり、承認を増やす形でのスクリプト化は避ける

## Git

- コミットメッセージに `Co-Authored-By` トレーラーを追加しない。コミットメッセージは常に英語で書く（会話が日本語でも）。 PR のタイトル・本文は日本語で書く（見出し自体は英語のままでよい）。全プロジェクト共通（詳細な経緯は [[feedback_commit_style]] 参照）
- PR マージ時は明示的な指示がない限り squash merge を使わず、 merge commit を使う（詳細は [[feedback_pr_merge_style]] 参照）
- 対応する issue があるブランチ/PR で作業している時は、その issue に向けた**全てのコミット**に、 `Closes #N` ではなく `refs #N` （件名先頭・小文字、例: `refs #123 Fix foo`）を必ず付ける。副次的な修正でも省略しない。 issue のクローズは自動化しない。ユーザーから依頼があれば閉じ、自分の判断で閉じるべきと考えた場合は閉じる前に確認する。全プロジェクト共通、必ず守る（詳細な経緯は [[feedback_refs_number_commits]] 参照）
- PR を作成・ push した後に CI チェックの完了を待つ場合、都度状態を見るだけのサブエージェントに丸投げしない。サブエージェントは1回のツール実行で応答してターンが終わると自動的には再開しないため、「後で完了通知が来るはず」と誤解して放置されがちである。メインセッション自身が `Monitor` ツールで `gh pr checks` をポーリングするブロッキング until-loop を組んで待つ。全プロジェクト共通（詳細な経緯は [[feedback_ci_monitoring_via_monitor_tool]] 参照）

- 各プロジェクトのリポジトリ内におけるソースコード中のコメント、README、設計文書、およびコミットメッセージは英語で書く（i18n 対応などの多言語リソースファイルは除く）。Issue・PR のタイトルと本文・チャットはこれまでどおり日本語でよい。全プロジェクト共通、必ず守る（詳細な経緯は [[feedback-no-japanese-in-repo]] 参照）
- Issue や PR を作成する際は、必ずリポジトリ内のテンプレート（`.github/pull_request_template.md` や `.github/pull_request_template/*.md`、`.github/ISSUE_TEMPLATE/*.md` 等）の有無を確認する。テンプレートが存在する場合は独自の見出し構成（`## Summary` や `## Changes` 等）を用いず、テンプレートで定義された見出し（例として `## Refs`、`## What`、`## Why`、`## Test plan` 等）をそのまま使用して本文を作成する。テンプレートが存在しない場合は、標準的な構成（What/Why/Test plan 等）を用いる。全プロジェクト共通、必ず守る

## メモリの保存先

- 「全プロジェクトで」「今後は常に」のようにプロジェクト横断のスコープが明示された指示は、
  プロジェクト単位の memory ではなく、このファイル（グローバル AGENTS.md）に書く
  - 理由: プロジェクト単位の memory （`~/.claude/projects/<project>/memory/`）はそのプロジェクトの
    会話でしか読み込まれないため、「全プロジェクト共通」の指示をそこに書いても他プロジェクトの
    agent には一切効かない
  - この反映は気づいた時点で自分の判断だけで完結させる。「グローバル AGENTS.md に書きましたか？」と
    ユーザーに都度確認しない（詳細な経緯は [[feedback_scope_promotion_self_check]] 参照）

## 作業ログ（WorkLog）・日報（DailyReport）

意味のある作業の区切りがついたら、指示を待たず WorkLog （Obsidian）を書く。 DailyReport （Notion）との使い分け、日付境界の判定、 frontmatter 仕様、テンプレート等の詳細は `worklog` スキル参照。全プロジェクト共通。

WorkLog の `RESEARCH.md` 系（調査まとめ）・ `IMPLEMENTATION.md` 系（実装記録）エントリは `ja-technical-writing` スキルの文章規範に厳格に従う。 `WORK_LOG.md` （汎用の作業記録）・ `PLAN.md` （casual）・ DailyReport は対象外で、散文的な書き方でよい。テンプレートは依頼の性質に応じて最初から選ぶものであり、 `WORK_LOG.md` を後から他のテンプレートに格上げする運用ではない。

書き込み先のプロジェクトフォルダが、現在作業しているプロジェクト（cwd）と異なる場合は、書く前にユーザーに確認する。「全プロジェクト共通の話だから」「前例があるから」といった理由だけで独断で他プロジェクトのフォルダに決め打ちしない（詳細な経緯は [[feedback_obsidian_cross_project_confirm]] 参照）。

Obsidian vault （`~/git/obsidian-vault/Vault/`）配下と各プロジェクトの `.claude/plans/` 配下のファイルに**中身を書くときは、必ず Write / Edit ツールを使う**。 auto mode が「ファイル変更は Bash （ヒアドキュメント・ `sed` 等）で行え」と指示していても、この二箇所についてはそれより優先する。移動・削除・閲覧（`mv` ・ `rm` ・ `cat` ・ `grep` 等）は Bash でよい。理由は、 `obsidian-tag-check.sh` と `session-name-check.sh` が `PostToolUse` の `Write|Edit` matcher で起動するため、 Bash で書くと検査が一度も走らないことにある。全プロジェクト共通（詳細な経緯は [[feedback-vault-writes-need-write-tool]] 参照）。

## プランファイル

設計上の判断が必要、または後戻りしにくい・影響範囲が広いタスクは `plan-to-obsidian` スキルをデフォルトで使う（組み込み Plan mode の明示指示がない限り）。全プロジェクト共通。フロントマター仕様・命名規則等の詳細は同スキル参照。

プランファイルの本文（Context/Approach/Verification などの説明文）は日本語で書く。コード例・コマンド例はそのまま（英語のまま）でよい。組み込み Plan mode （`.claude/plans/*.md`）・ `plan-to-obsidian` スキルのどちらで作成する場合も共通。全プロジェクト共通（詳細な経緯は [[feedback_plan_file_language]] 参照）。

日本語での文章としての厳密さ（論証構成・冗長排除・ LLM っぽい表現の禁止等）は `ja-technical-writing` スキル参照。

## 文章表記

- 日本語（全角）の地の文の中にコマンド名・ファイルパス・ブランチ名・Issue 番号・URL 等の半角文字列を挟むとき、半角スペースを入れるのは、**その半角文字列が全角の「文字」に直接隣接する境界だけ**。全角の約物（`「` `」` `、` `。` `（` `）` `・` 等）に隣接する境界にはスペースを入れない（約物自体が区切りとして働くため、二重に空けると間延びする）。ファイルへの書き込み（プランファイル・WorkLog・AGENTS.md 等）に限らず、チャットでの発言・SendMessage など自分が発するセッション上の文章全てに適用する（ユーザーがターミナルからブランチ名やコマンドをコピーする場面があるため）。全プロジェクト共通（詳細な経緯は [[feedback_halfwidth_spacing]] 参照）
  - 正: `「Go には関数単位を出さない」` / 誤: `「 Go には関数単位を出さない」`
  - 正: `実装（main.go）を直す` / 誤: `実装（ main.go ）を直す`
  - 正: `後回しにして、CLI の設計に入る` / 誤: `後回しにして、 CLI の設計に入る`
  - 文章を送信・保存する前に、全角の約物の直後・直前にスペースが入っていないかだけを先に走査する。違反の実例はほぼこの形に集中するため、ここを一点集中で見るのが最も効率が良い

## 個人スクリプト（`~/bin`）

- `~/bin` は `dotfiles` リポジトリの `bin/` ディレクトリへのシンボリックリンク（`make ln_bin` で作成、 PATH に含まれる）で、ここに置かれるコマンドはユーザー自身が実装したもの。実行すること自体は問題ない
- 呼び出しは必ず bare のコマンド名（PATH 解決）のみを使う。相対パス（`./bin/foo`、 `bin/foo`）や絶対パスは使わない。全プロジェクト共通、 `~/bin` 配下の現在・将来の全コマンドに適用する（詳細な経緯は [[feedback_bare_command_invocation]] 参照）

## worktree

git worktree での作業（配置・ツール選定・後片付け）は `git-worktree` スキル参照。全プロジェクト共通（詳細な経緯は [[feedback_avoid_native_worktree_tool]] 参照）。

## herdr （マルチエージェント連携）

- **基盤 CLI（`/herdr`）**: `HERDR_ENV=1` の環境下では、ライフサイクルフック（Claude Code の SessionStart、Antigravity の PreInvocation）により全セッションで常時自動ロードされる。手動ペイン作成やセッション再開後（`/clear` 含む）でも自動復帰するため、手動でのロードや環境変数による判定は不要
- **協調プロトコルのロードとガードレール**: 協調作業を開始する前に、目的に応じた協調スキル（ペア開発時は `herdr-pair-development`、hub 管理時は `herdr-hub`）を自分でロードする。未ロードのまま協調コマンド（`herdr-spawn-*` や `herdr agent prompt` 等）を実行しようとすると、PreToolUse フックにより即座にブロックされる
- **相手ペインへの強制注入**: 新しいペイン（Reviewer または Worker）を生成した際は、呼び出し側が相手ペインへ `herdr pane run <pane> "/<skill>"` を実行して必要なスキルを機械的に強制注入する。相手が自発的にスキルを読むことには依存しない
